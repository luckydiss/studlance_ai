**Уже принятое архитектурное решение о пробеле API:** в текущем коде нет admin GET исходников, а `Revision` не перечисляет вложения. Поэтому в PR 6 обязательно реализуй дополнение из 04/08: admin GET `/api/admin/jobs/{id}/input/{path}` и `AdminInputFile {path,size,revision}` в admin detail. `revision` берётся из существующего `files.version` (0 исходник, n вложение доработки n), не вычисляется по пути; существующий `FilesByJob` позволяет читать эти метаданные без миграции. Список группируется по номеру доработки, скачивание использует точный path этого списка. GET проверяет admin-роль, job id и `kind=input`, находит запись файла и открывает её сохранённый blob key; не допускает произвольный ключ/чужой заказ/crop/`..`, отдаёт файл потоково с Content-Disposition. Anonymous → 401, client → 403, неизвестное/недопустимое → 404. Worker token/lease в браузере запрещены. Обнови OpenAPI, сгенерированные Go/TS и HTTP-тесты; клиентский InputFile, worker-протокол и таблицы не меняй. Это согласованная часть PR 6, дополнительного разрешения не требуется.

## Что реализовать

**Маршруты и доступ.** `/admin` → `/admin/jobs`; `/admin/jobs/:id`, `/admin/clients`, `/admin/workers`, включая прямое открытие/перезагрузку. Тёмная шапка: «studlance · пульт», все три ссылки, почта и выход. Не показывай приватные экраны и не начинай admin-запросы до подтверждения роли `admin`. Общий вход находится в клиентской SPA на `/login`: переход между двумя приложениями действительно загружает нужную SPA. Неавторизованный пользователь получает безопасный локальный `next` и после входа админа возвращается туда. Клиент при открытии пульта направляется на `/login`, откуда действующая клиентская сессия может штатно вернуться на `/`; петли в пульт и истечения клиентской сессии из-за 403 быть не должно. Проверка роли только в UI не заменяет проверку API.

В `LoginPage` проверенный локальный `next` с pathname `/admin` или префиксом `/admin/` для admin-аккаунта требует полной браузерной навигации (например, `window.location.replace`), а не `navigate` клиентского React Router. Для клиентских путей сохрани штатную SPA-навигацию; для client-аккаунта admin-next не используется. Сохрани безопасную проверку адреса и регрессию единственного POST/next созданного заказа из PR 5.

**Сессии и ошибки.** Кеш admin отделён от client и привязан к пользователю; callbacks, poll и SSE захватывают поколение сессии/карточку при запуске. Поздние 200/401/SSE после выхода, смены пользователя, повторного входа того же админа или перехода в другой заказ не меняют новые данные, маршрут, форму и toast. Текущий 401 прекращает запросы, polling/SSE и очищает приватный кеш до входа с корректным адресом возврата. При переходе между SPA не полагайся на сохранность модульной переменной из другого приложения. Сеть — состояние повтора, 404 — «Заказ не найден» без старого заказа, 409 — сообщение плюс актуализация карточки. Pending мутации не допускает двойного отправления.

**Заказы.** Все колонки из 08, новые сверху, polling 10 с. Совместные фильтры статуса/внимания/поиска, состояния loading/error/empty. Сохраняй фильтры в URL при переходе в заказ и обратно. Группы статусов: «в работе» = queued/running/revising, «ждут ответа» = needs_input; done/failed/canceled — соответствующие группы, «все» включает uploading. API принимает один точный `status`, `attention`, `q`; групповой фильтр реализуй без выдуманных значений контракта. Из клиентов открывай `/admin/jobs?client=<id>` и фильтруй именно `job.client.id` (в API сейчас нет `client_id`).

**Разбор заказа.** Компоновка по AdminReview: шапка заказа с клиентом, состоянием/этапом, версией, попыткой, воркером, lease и ошибкой; слева трейс около 380 px, центр листы, справа около 320 px проверка/доработки/исходники/события/заметки. При узком окне колонки должны оставаться доступны через разумную прокрутку/адаптацию, без обрезанных действий. Не заменяй отсутствующие данные фиктивными числами или макетными документами.

**Трейс.** Все agent runs по порядку со временем, длительностью, исходом, tokens/cost при наличии и реальной ссылкой на raw log. Историю каждого run загружай через `GET …/runs/{run_id}/steps?after_seq=` до конца, максимум 500 шагов за ответ. `snapshot`/`job` содержит деталь, не полную историю steps; отдельные `steps` содержат run_id и пачку. Объединяй HTTP/SSE по `(run_id, seq)`, без дублей и потерь. Live-пачка, пришедшая во время загрузки, не должна перескочить незагруженную историю. После разрыва SSE — backoff 1→2→5→10 с, snapshot и добор пропущенных steps через HTTP. При смене карточки/выходе закрывай подписку, запросы и таймеры. Фильтр типа и раскрытие payload работают для всех загруженных шагов; вывод отображается как текст. Для 2 000 шагов нужен ограниченный DOM/виртуализация или дозагрузка, payload только по требованию; последний шаг реально доступен. Auto-scroll только пока пользователь внизу: прокрутка вверх не отыгрывается новым шагом, явный возврат вниз возобновляет слежение.

**Документы.** Черновик и все готовые версии, список документов/страниц, просмотр и скачивание через `/api/admin`. «Показать правки» включает настоящие changed_boxes с оранжевыми рамками, координаты корректны при масштабировании. Замечания клиента показываются с текстом/рамками и ссылками на правильный документ, страницу и исходную версию; поле номера доработки не считай номером листа, на котором замечание создавалось. При смене версии/документа старый лист не остаётся под новой подписью. Verification с severity/description без координат — список; привязки к листу не выдумывай. Пустой draft/pages/verification — явное состояние. Файлы с папками и пробелами скачиваются по точному пути, кодирование ровно по контракту, без trim и потери сегментов.

**Действия.** Ответ за клиента при needs_input; повтор только failed; отмена при допустимом состоянии; снятие needs_attention; заметка. Используй существующие admin POST. После действия обновляется реальное состояние и события; заметка сохраняется после reload. Отмена ожидает canceled сервера. Готовые работы по-прежнему выдаются автоматически, новую кнопку одобрения не вводи.

**Клиенты и воркеры.** Все поля из 08, клиент ведёт на заказы по точному id; воркер показывает online/last_seen/capabilities/info и ссылку на текущий заказ. Отсутствующий current_job/версии CLI — корректное пустое значение, не фиктивный заказ. Обновление позволяет увидеть смену online, без таймеров после ухода со страницы.

## Обязательные доказательства и тесты

Расширь существующий Playwright harness с настоящими Go server/worker и fakeagent, отдельными данными. Для подготовки синтетических состояний допустим API; проверяемые действия выполняются через UI. Не заменяй весь набор моками. Моки допустимы адресно для доставки старого ответа, сетевого сбоя и особых краёв; в отчёте отделяй их от настоящей интеграции.

1. Вход админа и return next между SPA; прямой deep link + reload. Client/anonymous не видят пульт и не запускают admin-запросы до проверки роли; прямой API для клиента возвращает 403, anonymous — 401; нет циклов редиректа и раскрытия предыдущего admin-кеша.
2. Заказы двух synthetic клиентов, все колонки, поиск, совместные фильтры/внимание, возврат из карточки; переход из клиента фильтрует точный id.
3. Во время настоящей работы появляются live steps; по окончании видны черновик/финал и raw log. Переключение документа/версии и changed_boxes; доработка с клиентским замечанием ведёт на правильный лист.
4. `#ask`: ответ админа через UI продолжается до done и фиксируется как admin. Постоянный `#fail-verify`: ошибка и внимание; ручной retry корректно отправляется и может снова завершиться failed. Отдельно `#fail-verify-twice`: после исчерпанных двух сбоев retry через UI достигает done — успех не подделывать.
5. `#hang` + отмена через UI → фактический canceled; снятие внимания; создание заметки и reload сохраняют её. 409 при изменившемся состоянии не показывает ложный успех.
6. Завершённый заказ с 2 000 шагов: несколько HTTP-пачек, первый/последний шаг после открытия и reload, фильтр типов, раскрытие последнего payload, прокрутка без блокировки управления. Сохрани измерение длительности действия/количества DOM-строк и метод воспроизведения, а не только фразу «быстро». Отдельно live-пачка во время истории и разрыв SSE с пропущенными шагами: все seq восстановлены без дублей; прокрутка вверх удерживается при новых шагах.
7. Клиенты/воркеры: правильные поля, online/offline и переход в текущий заказ. Нет фоновых запросов/таймеров после выхода и смены экрана.
8. 401/403/404/сеть; поздние ответы прежней сессии (включая повторный вход того же админа) и прежнего заказа. Observer до доставки исключает даже краткую вспышку чужой карточки. Для задержанного запроса сначала дождись его начала, зарегистрируй ожидание до release и дождись фактической доставки/response.finished(); если запрос действительно отменён, явно докажи отмену и непоявление данных вместо заявления о доставке. Фиксированная пауза не доказывает сценарий.
9. Полный принятый набор PR 5 остаётся зелёным. Не удаляй проверки точных байтов/next/поколения сессии и не ослабляй assertions ради успеха.

10. Новый admin GET input: настоящий UI download исходника и вложения доработки с точным сравнением байтов, папками и пробелами; корректная группировка по revision. Отдельный исходник с путём `input/revision-2/…` остаётся исходником (`revision=0`), независимо от похожего имени. HTTP-тесты anonymous/client/admin, неизвестный заказ/файл, тот же path у другого заказа, `..` и crop; ничего из другого job/kind не выдаётся. Путь для настоящего вложения имеет штатный `input/revision-<n>/…`, но номер связи берётся из метаданных.

Прогоны: frozen install, `pnpm -C web lint`, `pnpm -C web test`, `pnpm -C web build`, полный `pnpm -C web/e2e e2e`, `go vet ./...`, `go test -race -count=1 ./...`, `go test -race -count=1 -tags e2e ./e2e/...` с Poppler. Сначала web build, затем Go build/test для актуального go:embed. В окружении без CGO/gcc честно запусти Go без race и укажи ограничение, race подтверждается CI. Новый PR должен иметь зелёный CI с полноценными admin-тестами, Generate и Windows build. Не засчитывай help/неудачный launcher/no-tests как тесты.
