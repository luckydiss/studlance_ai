## Подтверждённые замечания

### 1. P1 — файл после нормализации занимает путь папки

Код: `internal/worker/localnames.go:108–115`; скачивание — `internal/worker/jobdir.go`.

Воспроизведение: сервер отдаёт разные файлы `a:b` и `a_b/child.txt` с правильными SHA. Отображение выдаёт `a_b` и `a_b/child.txt`. Первый файл скачивается, для второго создание папки `input/a_b` завершается ошибкой: на этом месте уже файл. Тест `TestRound3FileDirectoryCollision` падает на Windows.

Причина: `byLocal` проверяет только совпадение полного пути, не занятость промежуточных сегментов файлом. Суффикс последнего сегмента проблему предка не решает.

Ожидание и решение: отображение учитывает дерево с разными типами узлов «файл»/«папка». Суффикс применяется к конфликтующему сегменту; оба файла сохраняются, скачивание и Markdown используют одну устойчивую карту. Обратный порядок списка и перезапуск также должны работать.

### 2. P1 — вырезка доработки перезаписывает вложение клиента

Код: `internal/worker/revise.go:36,50,161`; серверные ключи — `internal/httpapi/client_handlers.go:305–308` и `internal/httpapi/worker_handlers.go:557–563`.

Воспроизведение: вложение доработки с серверным путём `revision-2/remarks/1.png` скачивается в input. Подготовка замечания №1 пишет вырезку в тот же файл. Тест `TestRound3CropOverwritesAttachment`: исходные 24 байта заменены на 124 байта PNG. Если вложение уже является валидным PNG, проверка `validCrop` ошибочно признаёт его вырезкой.

По коду подтверждена также серверная коллизия: приложенный к доработке `remarks/1.png` и вырезка №1 получают одинаковый `blob_key`. `Put` перезаписывает вложение до регистрации crop; уникальность `files.blob_key` мешает регистрации, а обработка ошибки удаляет этот ключ. Этот серверный край в данном раунде подтверждён чтением кода, отдельного успешного HTTP-воспроизведения нет.

Решение оркестратора: отдельное пространство для вырезок. Локально — `revision-crops/<n>/<idx>.png`, в blobs — `jobs/<job_id>/revision-crops/<n>/<idx>.png`, для записи `kind = crop` — путь `revision-crops/<n>/<idx>.png`. Входные файлы остаются в input. HTTP endpoint загрузки вырезок сохраняется. Запрещать клиенту имя `remarks/1.png` не требуется. Уточнены 02, 04, 05 и архитектура.

### 3. P1 — много коротких шагов обходят предел памяти

Код: `internal/worker/agents/run.go:410–437`.

Воспроизведение: сеть недоступна, парсер отдаёт миллион валидных `agent_message` с текстом `x`, каждый сразу Drain → очередь. Парсер пуст, очередь принимает все шаги. `TestRound3SmallStepsMemoryBound` зафиксировал учёт 1 000 000 байт при приросте удержанного heap 87 255 392 байта, то есть около 83 МиБ при лимите 50 МиБ.

Причина: `stepSize` считает только длины summary и JSON payload. Структуры NewStep, массив размеров, ёмкость slices и карты не учитываются. Пустые шаги могут расходовать нулевой бюджет, хотя удерживают память.

Решение: консервативный бюджет учитывает фиксированную стоимость шага и его удерживаемые структуры, общую очередь и отправляемую пачку. Нужен конечный предел количества шагов, включая пустые. Лишнее остаётся в полном сыром логе; чтение процесса не блокируется. Регрессии на больших payload сохраняются, добавляются короткие/пустые события и проверка освобождения памяти после восстановления сети.

### 4. P2 — HTTP retry повторяет commit после известной отмены

Код: `internal/worker/snapshot.go:213–216`, `internal/worker/job.go:181`, `internal/worker/client/client.go:319–351`.

Внешние проверки отмены исправлены, но внутренний цикл HTTP-клиента живёт на контексте, который при отмене заказа не закрывается. Проверка перед первым вызовом не распространяется на повторы внутри него.

Живое воспроизведение: прокси задерживает первый POST snapshot/v1/commit; клиент отменяет заказ; heartbeat подтверждает `cancel:true`; прокси возвращает 500, не передав запрос серверу. Воркер повторяет POST после подтверждённой отмены, сервер отвечает 204. Итог canceled, однако документы v1 уже зарегистрированы в БД. `live-b.log` содержит обе попытки с `confirmed_cancel:true`.

Тест `TestRound3CancelOnCommitRetry` подтверждает тот же край для draft/v1/v2. `TestRound3CancelOnFinishRetry` показывает повтор `finish ok` после отмены. Для finish доказательство тестовое; живой сценарий finish не завершён. Сервер защищает финальный статус, поэтому утверждения о выдаче canceled-заказа как done нет.

Решение: отдельный отменяемый контекст активной работы и её HTTP-запросов, который закрывается при известной отмене/потере lease. После отмены новые попытки загрузки снимка/вырезки, commit и finish ok не начинаются. `finish canceled` имеет отдельный рабочий контекст. При stale_lease любой finish запрещён. Запрос, отправленный до отмены, мог успеть выполниться — тестировать следует новые попытки после известной отмены.
