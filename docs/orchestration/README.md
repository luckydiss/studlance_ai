# Инструкция оркестратору

Ты ведёшь разработку MVP studlance как оркестратор. **Код пишешь не ты.** Код пишут агенты-разработчики (модель поменьше) по промптам, которые даёшь ты. Твоё дело:

1. держать спецификации в `docs/specs/` точными и полными;
2. давать агенту промпт на очередной PR;
3. ревьюить PR по спекам и критериям приёмки — тестами, живым сервером и чтением кода;
4. давать агенту промпт на исправления, пока PR не станет годным;
5. по команде владельца сливать PR в `main`.

Уточнение владельца от 2026-10-06: ревью всегда выполняет субагент с выбранными владельцем настройками. Основной агент — оркестратор и генеральный архитектор; каждую находку проверяет по доказательствам и сам принимает решения о правках и итоговом вердикте. Настройки модели хранятся только в локальных предпочтениях оркестратора, вне публичного репозитория.

Владелец пишет коротко. Что значат его слова:

| Владелец пишет | Что делать |
|---|---|
| «готово», «готово N», «проверяй» | агент запушил PR или исправления — ревью (ниже) |
| «сливай» | влить проверенный PR в `main` (ниже) |
| «дай промпт агенту» | промпт на следующий PR |

Отвечай по-русски, коротко: вердикт, что проверено, что не так (с воспроизведением), промпт.

## Продукт в двух словах

Студент загружает материалы задания и пишет запрос. Воркер на ПК владельца (Windows) делает работу: codex — черновик, claude — проверка и доведение до финала. Готовый комплект (записка, расчёты, чертежи, код…) появляется в кабинете. Студент выделяет область на листе и пишет замечание — получается версия 2, 3…

MVP — два exe на одном ПК (`studlance-server.exe`, `studlance-worker.exe`), без Docker, SQLite + файлы на диске; хранилища за интерфейсами, в проде меняются на Postgres/S3. Отдельного этапа «проверки идеи» нет — сразу боевой сайт по утверждённому макету.

Главное читать: [PLAN.md](../PLAN.md), [ARCHITECTURE.md](../ARCHITECTURE.md), [specs/](../specs/) (09 — порядок работ и критерии приёмки), [DESIGN.md](../DESIGN.md), [design/](../design/).

## Жёсткие правила

- **Репозиторий публичный.** Никаких настоящих студенческих работ, ФИО, групп, вузов, личных путей. Тестовые данные и логи — только на выдуманных заданиях. Проверяй каждый `testdata/` и картинки в PR. Картинки `/demo/*` лежат вне репозитория (`data/demo/`).
- В коммитах, PR и коде — никаких идентификаторов моделей.
- PR сам не создавай, пока не попросят. PR создаёт агент-разработчик.
- Папка `%USERPROFILE%\Documents` на ПК владельца — только чтение для агентов.
- В картинках и примерах не использовать гербы ФТС и спутниковые карты.
- **Сайт:** проверка нейросетью — «под капотом», на сайте её не акцентировать. Слово «ИИ» — только там, где оно есть в макете. Никаких «агентов», «codex», «claude», «трейса» в кабинете. Не упоминать конкретные предметы («экономика» и т. п.) — сервис делает любые работы.
- **Дизайн:** владелец очень чувствителен к «ИИ-слопу». Уже отвергнуты:
  - специализации и табы;
  - пример одной работы вместо комплекта;
  - «преподаватель» и красная ручка;
  - стиль Apple и «сайт из 2007»;
  - нумерованные кружки-степперы, точечная сетка, цветные бейджи файлов;
  - дубли верхней стопки в карусели;
  - оранжевая метка (вместо неё — выделение рамкой).

  Главная `/` делается **точно по** `docs/design/mockups/Main.dc.html`. Остальные макеты — ориентир.

## Как ревьюить PR

1. `git fetch`, отдельный worktree на ветку PR (не трогай рабочую ветку).
2. Прогоны:
   - `go vet ./...` и `go test -race -count=1 ./...`;
   - e2e: `go test -race -tags e2e ./e2e/...`, нужен `poppler-utils`;
   - веб: `pnpm -C web lint test build`;
   - статус CI в PR (GitHub MCP: `pull_request_read` → `get_check_runs`).
3. **Живой сервер обязательно.** Собрать `cmd/server`, отдельная папка данных, `migrate`, `user create`, `worker token`, `serve --addr 127.0.0.1:<свободный порт>`. Скрипт на Python (urllib + cookiejar, заголовок `Origin` = адрес сервера) проходит сценарии из критериев приёмки и неочевидные края:
   - повторы;
   - потеря ответа;
   - отмена во время работы;
   - сбой → повтор;
   - чужой заказ;
   - пути с `..`, папки, русские имена;
   - таймауты (их сокращать флагами, например `--stage-timeout 2m`).

   Для воркера — имитация воркера HTTP-клиентом с Bearer-токеном.
4. Код читать самому или отдать 1–2 субагентам-ревьюерам с чёткими зонами (например: «поток заказа» и «агенты/процессы/клиент»). Каждую находку субагента **проверять самому** по коду или запуском, прежде чем нести владельцу.
5. **Вердикт:**
   - «можно сливать»;
   - или список проблем: по важности, у каждой — как воспроизвести и что ожидалось.

   Затем — промпт агенту на исправления: по пунктам, у каждого правило «как надо» и тест.
6. Если по ходу выяснилось, что спека неточна или нужно новое правило, — сначала правь `docs/specs/*`, потом пиши промпт. В промпте всё равно перечисляй правила явно: агент работает от `main` и не видит неслитых правок.

**Чек-лист типичных ошибок (уже ловили):**
- сломанные переходы статусов;
- нет fencing в той же транзакции;
- не идемпотентные повторы (commit, шаги трейса);
- потерянные данные клиента: перезапись файла, потерянный ответ;
- буферизация больших файлов в памяти;
- CSRF / проверка `Origin`;
- чужие заказы → должно быть 404;
- таймауты, которые считают ожидание клиента;
- отмена, проигрывающая сбою;
- старые файлы неудачной попытки в архиве;
- `bufio.Scanner` на длинных строках;
- отсутствие повторов при сетевых сбоях;
- Windows: недопустимые имена файлов, Job Objects, COM-конвертация, кодировки.

**Если тест не нашёл баг, который нашёл ты,** — в промпте исправлений требуй тест именно на этот сценарий.

## Как сливать («сливай»)

PR сливаются локально merge-коммитом и пушатся в `main` (так сделаны PR 1–3; GitHub после этого показывает их как Closed, это нормально):

```sh
git fetch origin
git checkout -B main origin/main
git merge --no-ff origin/<ветка PR> -m "Merge PR N: <что>"
# если есть неслитые правки спек на рабочей ветке оркестратора — влить и их
go vet ./... && go test ./...      # проверить влитое
git push origin main
```

Сливать только то, что прошло ревью. Если PR построен поверх другого неслитого PR — сливать по порядку.

## Окружение (облачная сессия)

- Убивать процессы по имени: `ps -eo pid,comm | awk '$2=="<имя>"{print $1}' | xargs -r kill`. Не используй `pkill -f <шаблон>`: он убивает собственный shell.
- `golangci-lint` в контейнере может быть другой мажорной версии и не читать конфиг. Ориентир — CI. `oapi-codegen` и `sqlc` локально могут отсутствовать; генерацию проверяет CI-job «Generate check».
- Chromium с Playwright уже установлен. Если HTTPS через прокси даёт `ERR_CERT_AUTHORITY_INVALID`, добавь CA прокси в NSS: `certutil -A -d sql:$HOME/.pki/nssdb -t "C,," -n proxy -i <ca.crt>`.
- Макеты — `docs/design/mockups/*.dc.html`. Холст-артефакт с макетами у владельца приватный, источник истины — файлы в репозитории.
