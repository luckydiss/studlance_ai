## 1. Устойчивое отображение имён учитывает файл и папку

Сейчас `a:b` становится файлом `input/a_b`, а другой допустимый вход `a_b/child.txt` требует папку по тому же пути. `localnames.go` проверяет только равенство полного пути, поэтому второй download падает.

Правило: отображение серверных путей строится с учётом дерева сегментов, сравнения Windows без регистра и типов узлов. Локальный файл не может быть папкой или предком другого файла. Разрешай коллизию устойчивым суффиксом в конфликтующем сегменте. Сохраняй вложенность и правильные байты всех файлов. Одна карта используется для download, TASK.md, Files промпта и REVISION-N.md. Порядок входного списка не должен влиять на результат; корректные сохранённые отображения сохраняются при restart/retry и добавлении новых файлов.

Тесты: `a:b` + `a_b/child.txt`; `a_b` + `a:b/child.txt`; конфликт промежуточного сегмента в более глубоком пути; варианты регистра. Проверить оба порядка входного списка, SHA всех файлов и отсутствие пересечения файл/папка. Перезагрузить сохранённую карту, затем добавить конфликтующий вход: старые корректные пути остаются рабочими, новый получает безопасное имя. Каждый путь из Markdown существует и содержит свои байты. Сохранить прежние тесты коллизий полных имён.

## 2. Вырезки отделены от всех входных файлов

Сейчас вложение доработки `remarks/1.png` скачивается в `input/revision-2/remarks/1.png`; подготовка замечания №1 перезаписывает его вырезкой. Валидный PNG-вход ошибочно считается уже готовой вырезкой. Сервер пишет вложение и crop в одинаковый blob_key, а при ошибке регистрации может удалить входной blob.

Принятая структура:

- локальные вырезки: `revision-crops/<n>/<idx>.png` относительно папки заказа;
- blob_key: `jobs/<job_id>/revision-crops/<n>/<idx>.png`;
- запись `files` с `kind = crop`: `path = revision-crops/<n>/<idx>.png`;
- входные файлы клиента остаются в input, включая допустимое имя `remarks/1.png`;
- HTTP upload endpoint остаётся `PUT /api/worker/jobs/{id}/input/revision/{n}/remarks/{idx}`.

Обнови prepareRevision, пути в REVISION-N.md, обработчик загрузки crop и RecordRevisionCrop. Ссылка Markdown должна указывать на реальную новую вырезку; папку создаёт воркер, агент читает её. Сохрани атомарную запись, идемпотентность, восстановление отсутствующих/битых вырезок, fencing и повторы сети. Входные файлы не проверяй как готовые вырезки. Старые файлы в input не переносить и не удалять как собственные вырезки: новую вырезку можно восстановить из предыдущего снимка.

Тесты воркера: доработка с приложением `remarks/1.png`, отдельно произвольные байты и валидный отличающийся PNG; prepareRevision и повтор/continue сохраняют вложение побайтно и создают правильную вырезку отдельно. Удаление вырезки восстанавливает её, не трогая вход. Тест серверного API: приложить `remarks/1.png`, загрузить crop №1 и повторить upload; SHA/байты входа до и после одинаковы, запись crop и её blob отдельные. Проверить также начальный вход `revision-2/remarks/1.png`, чтобы он не пересекался с crop, и ошибочный upload/fencing: откат не удаляет входной blob. Не ограничивать имена клиента вместо разделения пространств.

## 3. Предел памяти работает и для коротких/пустых шагов

История парсера и удержание больших хвостов уже исправлены. Остался `stepSize`: длина summary плюс сериализованный payload не учитывают сами NewStep, slices, массив размеров и карты. Миллион событий с текстом `x` даёт учёт 1 МБ при удержании около 83 МиБ.

Правило: общий лимит 50 МиБ охватывает удерживаемые данные парсера, очередь и отправляемую пачку, включая фиксированную стоимость каждого шага, ёмкости контейнеров и карты payload. Используй консервативный расчёт и конечный предел числа шагов. Пустой шаг тоже расходует бюджет. JSON-размер не подменяет оценку памяти. Отправленные и отброшенные структуры освобождаются; лишнее остаётся в полном сыром логе, seq может иметь пропуски. Сеть не блокирует чтение stdout/stderr.

Тесты: миллион коротких валидных событий; пустые summary/payload; смесь коротких и больших payload при заблокированной отправке и с пачкой in-flight. Очередь достигает конечной границы и отбрасывает лишнее; проверка удержанного heap после GC выявляет исходное превышение с разумным допуском на runtime, а не зависит от точного числа аллокаций. После восстановления сети принятые шаги доходят, память освобождается, сырой лог полный. Сохранить прежние регрессии Drain, tail copy и учёта отправляемой пачки.

## 4. Известная отмена останавливает внутренние HTTP retries

Внешний cancel guard работает. Но после первого POST commit/finish внутренний цикл client.do повторяет исходное тело на живом контексте, даже когда heartbeat уже подтвердил cancel. Живой сценарий: первый commit удержан прокси → cancel подтверждён heartbeat → прокси возвращает 500, не передав запрос серверу → повтор commit получает 204 и регистрирует v1 у canceled-заказа. Для finish тест показывает `[ok ok]`.

Принятое правило: у активной работы и её HTTP-запросов отдельный отменяемый контекст. Он закрывается при подтверждённом cancel или потере lease. После известной отмены не начинаются новые попытки загрузки снимка/вырезки, commit или finish ok, включая повторы после 5xx, обрыва и потери ответа. Служебный finish canceled должен иметь отдельный действующий контекст задания и сохранять необходимые повторы. Stale lease прекращает работу без любого finish. Не создавать бесконечный цикл повторов context.Canceled и не выдавать отмену как failed/timeout.

Запрос, уже отправленный до отмены, мог успеть выполниться. Тестируем прекращение новых попыток после известной отмены, а не невозможную отмену уже выполненного серверного действия.

Тесты с управляемым backoff/heartbeat: первый запрос получает 500, до повтора приходит cancel; draft/v1/vN commit больше не отправляется, finish ok больше не повторяется, finish canceled выполняется. Аналогично для upload и сетевого обрыва/потери ответа. Отдельно stale lease во время ожидания повторной попытки: новых запросов и finish нет. E2e/живой сценарий с прокси, который не передал первый commit серверу: после cancel нет второго commit, нет новых документов соответствующего снимка, конечный статус canceled. Сохранить прежние сценарии обычной отмены во время загрузки/конвертации.
