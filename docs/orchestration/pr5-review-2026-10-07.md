## Обязательные исправления

### 1. P1 — заказ предыдущего пользователя остаётся видимым после входа другого

Места: `web/shared/src/auth.ts:47–49`, `web/shared/src/jobs.ts:18–23`, `web/client/src/pages/JobPage.tsx:35`.

В одной вкладке открыть заказ A, дождаться истечения сессии, войти B и через SPA вернуться по URL заказа A. Сервер отвечает 404, но `useLogin` меняет только `['me']`, ключ заказа не содержит пользователя, а `JobPage` отображает `query.data` до проверки ошибки. Поэтому под аватаром B остаются название и данные заказа A.

Воспроизведение — отдельный браузер с адресными mocks: `/me` 200 A, заказ 200; browser clock +61 000 мс; `/me` 401; login 200 B; прежний заказ 404. После входа URL повторно открыт через `history.pushState` без перезагрузки QueryClient. `auth-cache-leak.json`: `accountBVisible=true`, `cachedAOrderVisibleAfter404=true`, exit 0. Скриншот показывает `PRIVATE A ORDER` под аватаром AB. SSE здесь отвечает 204, утечку создаёт именно сохранённый REST-кеш. Это проверка клиента на синтетических данных, а не демонстрация обхода серверного доступа.

Требование: приватный кеш и подписки ограничены текущей сессией/пользователем; при её завершении и смене аккаунта очищаются, старые ответы не восстанавливают их. 404 имеет приоритет над сохранённым содержимым. Нужны регрессии A → B, отсутствия даже краткого показа старого заказа и запоздалого ответа/события.

### 2. P2 — 401 закрывает форму входа и теряет адрес возврата

Места: `web/shared/src/auth.ts:31`, `web/client/src/job/api.ts:25–29`, `web/client/src/pages/OrdersPage.tsx:36–37`, `web/client/src/pages/LoginPage.tsx:14`.

Пока `/me` свежий в кеше, GET заказа возвращает 401. Обработчик ведёт на `/login?next=…`, но LoginPage видит прежнего пользователя и сразу ведёт на `/`. Форма входа не появляется, next теряется. Адресный браузерный probe: `/me` 200 A → список → заказ 401; итог `finalUrl` с путём `/`, `loginFormVisible=false`, exit 0 в `auth-401-next-bounce.json`.

Требование: подтверждённый 401 завершает локальную сессию и открывает форму с безопасным next; успешный вход возвращает к исходной странице. Проверить список и карточку, в том числе поисковые параметры; обычный сетевой сбой не выдавать за 401. Эти правки можно сделать вместе с пунктом 1, но нужны обе регрессии.

### 3. P2 — разные имена файлов превращаются в один путь, один файл теряется

Места: `web/client/src/files.ts:15–18`, `web/client/src/files.ts:163–168`. Серверное правило для сравнения: `internal/jobs/jobs.go:225–247`.

Выбрать два разных файла `  report.txt` и `report.txt`. `trim()` удаляет пробелы из каждого сегмента, оба пути превращаются в `report.txt`; `mergeFiles` молча оставляет последний. Сервер пробелы не удаляет. Такие два файла с разными байтами дополнительно созданы на Windows в отдельной папке ревью: оба имени допустимы. Адресный Vitest воспроизвёл коллизию и потерю одного элемента, 1/1 pass; лог `targeted-space.log`.

Требование: сохранять допустимые исходные имена и относительную структуру; заменять только точно совпадающий путь. Нужны unit-регрессия и браузерная проверка двух реальных загрузок с разными путями/байтами, включая имя папки с пробелами.

### 4. P2 — visual harness всегда даёт ложный нулевой diff

Место: `web/e2e/visual-compare.mjs:71,81–82`.

Оба `getImageData` читают `(0,0,w,h)`, хотя второе изображение нарисовано на `y=h`: скрипт сравнивает первый скриншот с ним самим. Высота `min(heightA,heightB)` дополнительно отрезает несовпадающий хвост. `pnpm -C web/e2e run visual` завершился exit 0 с `changed=0` из 2 390 400 пикселей. Независимое сравнение исходных PNG тем же порогом суммы RGB >24 нашло 407 789 отличий (17,059%).

Это число не означает, что 17% вёрстки нарушают дизайн: у исходных снимков различались данные формы, этап карусели и fallback отсутствующих demo. Дополнительное сравнение в более близком состоянии дало 38 397 пикселей (1,606%); остаток сам по себе не принят как отдельный дефект продукта. Утверждение PR о нулевом diff недостоверно, визуальная приёмка не подтверждена.

Требование: независимые буферы, полные размеры, регрессии одинаковых/разных PNG и разных размеров; затем одинаковые состояния формы/карусели/шрифтов/demo, реальные скриншоты рядом и корректный diff. Техническая обёртка raw HTML допустима, исходные утверждённые макеты и их геометрия не меняются ради совпадения. Исправить визуальное утверждение в описании PR по результату нового прогона.

- Ошибка 413 на главной не оказалась тупиком: сохранённый uploading-заказ открывается через «Мои заказы», замена файла по тому же пути проходит настоящим PUT, после неё submit успешен. Адресный browser probe `targeted-413-recovery.log`: 1/1 pass. Отдельное расширение управления формой не требую.

- Клавиатурный способ создания прямоугольника отсутствует по коду PageCanvas. Отдельный способ выделения с клавиатуры не включён в этот раунд: действующая 07 явно задаёт мышь/палец, а новый способ требует отдельного продуктового решения. Это не подтверждение полной доступности; навигация страниц и существующих controls с клавиатуры по-прежнему обязательна.
- Пустой draft/file-only, верхний лимит prompt, submit gate и generated-контракт соответствуют согласованным уточнениям. Замечания связаны с исходной версией; флаги действий берутся из сервера, нарушения в проверенных путях не обнаружены.
