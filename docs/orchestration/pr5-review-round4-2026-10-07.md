## P2 — auth gate перезаписывает адрес возврата созданного заказа

Места: `web/client/src/pages/home/OrderForm.tsx:176–177`, `web/client/src/RequireAuth.tsx:24–28`; `expireSession` ставит `me=null` в `web/shared/src/auth.ts`.

Как воспроизвести:

1. Войти A, на главной выбрать файл и оформить заказ.
2. POST `/jobs` успешно создаёт заказ; PUT `/input` вернуть 401 при свежем cached `me` (в регрессии замокан только PUT, создание/вход настоящие).
3. `OrderForm` завершает локальную сессию и явно направляет на `/login?next=/orders/{id}`.
4. `RequireAuth`, уведомлённый об изменении `me`, может выполнить свой `<Navigate>` с прежним текущим маршрутом `/`.
5. Форма входа остаётся видимой, но URL становится **`/login?next=%2F`**, вместо адреса созданного заказа.

Доказательства на точном head:

- Полный Playwright с настоящим Go server/worker/fakeagent: **24 PASS / 1 FAIL**, exit 1. Падает новый `pr5-round4.spec.ts:14`: `no order next …/login?next=%2F`. Error-context содержит URL и видимую форму входа.
- Адресный повтор того же теста три раза: **1 PASS / 2 FAIL**, обе ошибки с `next=/`.
- Независимый Chromium/Vite с явно замоканным `/me` 200, созданием заказа и PUT 401: **1 из 5** запусков остаётся с `next=/` после фактического `response.finished()` и ещё 500 мс. Raw assertion содержит actual `/login?next=%2F`, expected `/login?next=%2Forders%2Forder-upload-401`; остальные четыре запуска проходят. Более поздняя ограниченная серия не дала новых сбоев, что не отменяет зафиксированную гонку.

Проверка адреса — функциональная гарантия, а не косметическое требование теста. По коду LoginPage его `safeNextPath` и `navigate` используют сохранённый next; неправильный `/` означает возврат на главную. В независимом неудачном запуске вход после неправильного next не завершали, поэтому этот вывод указан как следствие кода, а не отдельное наблюдение браузера. Дополнительный настоящий UI probe в одном удачном запуске сохранил правильный next сразу, через 500/1500 мс и вернул после входа в созданный заказ. Это подтверждает успешный порядок исполнения, но не отменяет неправильный next через 500 мс в независимом неудачном запуске; сохранение неверного адреса через 1500 мс отдельно не проверено.

**Решение архитектора:** адрес возврата созданного заказа должен иметь согласованный источник для формы и auth gate. При любом порядке уведомлений и эффектов `/orders/{id}` нельзя заменить исходной главной. Очистка приватного кеша и fencing старой сессии сохраняются. Добавление задержек, ослабление проверки next или успешный одиночный повтор не закрывают гонку. Требуется ограниченная правка клиентской навигации и регрессия конечного адреса/повторного входа в тот же заказ.
