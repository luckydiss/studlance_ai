## Контекст и границы

Сначала прочитай `docs/orchestration/README.md`, `docs/PLAN.md`, `docs/ARCHITECTURE.md`, `docs/specs/01-repo-build.md`, `03-lifecycle.md`, `05-worker.md`, раздел PR 7 в `09-tasks.md`, `docs/design/README.md`. Не придумывай флаги, поля TOML, службы Windows или команды restore.

MVP — два exe на одном Windows-ПК: Go-сервер, SQLite и файлы, воркер с настоящими codex/claude и локальными Office/КОМПАС. Кабинет и пульт уже реализованы и проверены. Не переделывай их, не добавляй Docker, Postgres, S3, публичный хостинг, оплату или регистрацию. Если установка выявляет дефект production-кода, сообщи точное воспроизведение оркестратору до расширения scope.

Только выдуманные пользователи/задания и общие пути вроде `C:\studlance`; никаких личных путей, настоящих работ, паролей, токенов, идентификаторов моделей в коде, коммитах, PR и публичных отчётах. Локальный `worker.toml` с токеном не коммитить. `%USERPROFILE%\Documents` только читать; checkout, сборка, тестовые данные и логи — вне этой папки. Сохрани чужую незавершённую работу.

На этом этапе разработай и проверь файлы PR в изолированном окружении. Не создавай учётную запись/задания автозапуска на ПК владельца, не устанавливай туда ПО, не читай личные CLI-сессии, не запускай настоящих платных агентов и не перезагружай ПК. Эти действия входят в отдельную установку и приёмку владельцем по готовой инструкции.

## Что сделать

1. **`docs/INSTALL.md` на русском.** Последовательная инструкция от чистой установки до работающего сайта. Два пути получения exe: скачать проверенный Windows-артефакт для конкретного SHA или собрать из исходников через `scripts/build.ps1`. Укажи Go из `go.mod`, Node 22/pnpm 9 и настоящий порядок web → Go; инструменты сборки отдели от необходимого runtime. Проверяй exit code внешних команд в PowerShell. Владелец должен понимать, что уже установлено, что проверить и какой результат ожидать.

2. **Отдельная учётная запись `studlance`.** Установка и вход в codex/claude именно под ней, КОМПАС-3D, Office, Python, Playwright/Chromium и Poppler; зависимости для подготовки файлов — по реальным промптам/задачам. Дай проверку версий, путей команд и `pdftoppm`, затем `worker probe --config <путь>`. `probe` показывает возможности, но не доказывает авторизацию CLI, работоспособность COM или завершение заказа. Если нужны ссылки/команды сторонней установки, проверь текущие официальные источники; не придумывай неподтверждённый пакет Poppler. Тестирование PR не должно устанавливать Office/КОМПАС на машину владельца.

3. **Постоянные пути и первый запуск.** Пример структуры `C:\studlance\server`, `worker`, `jobs`, `backups`, `poppler`. Используй один явно заданный абсолютный `--data` для migrate/user/token/serve/backup и `--config` для worker. Серверные команды не должны случайно создать вторую базу из-за смены cwd. Покажи миграцию, создание admin и client с безопасным вводом пароля, получение токена и его вставку в локальный конфиг, запуск сервера и воркера, `/healthz`, вход клиента и `/admin`, online воркер в пульте. Один origin в server_url и браузере. Пути с пробелами должны быть корректно заключены в кавычки.

4. **`worker.example.toml` уже существует.** Уточни его комментарии/примеры по реальным полям, сохрани пустой token и общие пути. Не дублируй TOML-секции. Объясни timeout/heartbeat, постоянство name/token/work_dir, команды CLI и дополнительные args без идентификаторов моделей. Токен выдаётся один раз, сервер хранит только хэш; потерянный токен из DB backup не восстановить, а повторный `worker token --name` с тем же именем завершится ошибкой. Конфиг с токеном нужен в отдельной защищённой копии. Новый worker ID не заберёт заказы, закреплённые за старым; не выдавай создание нового имени за восстановление. Для smoke допускаются fakeagent с корректными args для обоих CLI, но это отдельный тестовый конфиг вне репозитория, не основной профиль установки.

5. **Картинки `/demo`.** Только ручное копирование владельцем из `studlance_ai_private/demo/` в `<data>\demo`; имена, ширины и JPEG — по таблице `docs/design/README.md`, ссылка на неё обязательна. Приватные картинки не скачивать/не коммитить. Их отсутствие оставляет пустые листы; это предусмотренное поведение, не дефект дизайна. `/demo/` в Main.dc.html не заменять внутренними ссылками холста.

6. **Автозапуск и остановка.** Дай воспроизводимую настройку Планировщика Windows с явной рабочей папкой/аргументами/учётной записью, запретом параллельных экземпляров и восстановлением после сбоя. Для Office/КОМПАС выбери запуск в интерактивной сессии `studlance`: после перезагрузки требуется вход этой учётной записи. Не обещай работу COM как фоновой службы до входа пользователя. Пароли не помещать в скрипт или аргументы команд. Для фоновых PowerShell-helper процессов — скрытое окно. Опиши отключение автозапуска и корректный Ctrl+C; не убивай все Office/КОМПАС процессы по имени. Укажи, какие действия должен выполнить владелец через UI Планировщика.

7. **Обновление и резервные копии.** Сохранить постоянный data, worker.toml и рабочие папки work_dir/<job_id> со всеми `.studlance` состояниями/снимками. `.studlance/state.json` хранит идентификаторы CLI-сессий; сами CLI auth/session stores находятся в профиле Windows-учётки. Отдельно сохранить тот же профиль `studlance` и не сбрасывать его авторизацию/сессии CLI. Описать остановку воркера, затем сервера, backup на остановленных процессах для согласованности DB/blobs, замену только бинарников, запуск сервера, затем воркера и проверки. `backup --out` содержит всю `studlance.db`, включая серверные записи заказов/состояния, пользователей/сессии/хэши токенов, и `blobs`. Он не содержит demo, локальные рабочие папки из work_dir, worker.toml или CLI-профили/auth; дополнительные копии и их приватное хранение описать отдельно. Сам DB/blob архив тоже приватный. Приведи фактическую процедуру восстановления ZIP в новый пустой data при остановленных процессах и проверки; команды restore в CLI нет. Не восстанавливай старый DB поверх живого WAL. Не обещай автоматический откат схемы после миграции: возврат старых бинарников при необходимости сопровождается восстановлением совместимой копии. Поведение незавершённого заказа после перезапуска объясни по реальным lease/action continue и таймаутам, без обещания бесконечного resume: тот же worker ID может получить running-заказ сразу, даже до истечения lease, а таймаут этапа продолжает считаться с сохранённого времени старта.

8. **Исправить поставляемый Windows-артефакт.** Сейчас Windows build job собирает Go без web assets, поэтому успешный отдельный Web job не делает exe готовым к установке. Добавь frozen install и production build обоих фронтов до Go build в Windows job либо доказуемый перенос assets. В `scripts/build.ps1` также замени обычный install на frozen, чтобы локальная сборка использовала lockfile. Сохрани все существующие проверки. Smoke должен запускать именно exe из поставляемого комплекта в изолированном data и проверить `/healthz`, `/`, `/admin`, SPA deep links и загрузку JS/CSS обоих приложений с верными MIME. Заглушка/HTML вместо asset, только наличие файлов и только `--help` — не доказательство. Smoke запускает лишь сервер с синтетическими данными, не настоящих агентов.

## Проверки разработчика

- Сборка через Windows-скрипт с web, оба exe существуют; smoke именно комплекта поставки и тот же smoke в CI Windows build. Проверка example TOML настоящим загрузчиком; `probe` отдельно и с честным перечислением недоступных возможностей.
- На отдельной выдуманной базе пройти указанные в INSTALL команды migrate, user create, worker token, serve, backup; пароль и token не выводить в публичный лог. Сделать backup после остановки процессов, восстановить в новую папку, подтвердить вход и совпадение байтов хотя бы одного blob. Проверить старт с другим cwd при абсолютных data/config и путь с пробелами.
- Для проверки worker допускаются fakeagent и тестовые state/jobs. Реальный браузерный путь уже покрыт PR 5–6: не ослабляй 44 принятых Playwright-сценария. Для своих scripts/CI добавь адресные проверки поведения, не зеркальные тесты текста документации.
- Frozen install, web lint/test/build, затем Go vet и `go test -race -count=1 ./...`, Go e2e с Poppler, Playwright и Generate/Windows build должны оставаться зелёными в CI. Если локально race недоступен, укажи это и подтвердись CI. Записывай реальные команды и pass/fail/skip, различай smoke, fakeagent и настоящую приёмку.

## Чек-лист владельца — боевая приёмка

Подготовь отдельный удобный чек-лист со статусами «не проверено / прошло / не прошло», исходно всё не проверено. Для каждого шага — действие, ожидаемый результат и санитизированное доказательство; нельзя отмечать боевую приёмку пройденной на fakeagent/моках.

1. Три выдуманных работы с настоящими агентами: записка + Excel; чертежи КОМПАС; программа со скриншотами. В браузере путь от «Оформить заказ» до «Готово», реальные скачиваемые файлы открываются соответствующими программами, превью читается.
2. Замечание выделением области на листе → версия 2 с фактическим исправлением, предыдущая версия доступна.
3. Настоящий вопрос агента виден клиенту; ответ продолжает работу до результата.
4. В пульте видны настоящий трейс, черновик, финал и рамки реальных правок, воркер online.
5. Перезагрузка ПК во время работы выполняется владельцем: сохранить data/jobs/config, после входа `studlance` запустить сервер/воркер автозапуском; тот же заказ завершается без повторного создания. Зафиксировать stage/attempt, временные границы lease/timeout и результат. Остановка/старт процесса в developer smoke полезны, но не заменяют этот reboot с настоящим CLI.
