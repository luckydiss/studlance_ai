## 1. P2 — callbacks незавершённой мутации воздействуют на новую сессию

Места: `web/client/src/pages/JobPage.tsx:103–106`, `web/shared/src/jobs.ts:36–48`, `web/client/src/main.tsx:18–26`, `web/client/src/job/api.ts:27–34`.

Две адресные репродукции с обычным браузером и явно замоканными auth/job ответами, без настоящей БД:

1. A нажимает «Ответить», HTTP-ответ POST `/answer` задержан. `/me` становится 401, A входит заново, новая карточка уже показывает актуальные данные. Затем старый 200 доставляется: `onSuccess` пишет его через `setJobCache` в тот же ключ пользователя A. MutationObserver записал **одно появление старого заголовка**; последующая invalidation через секунду вернула актуальный заголовок. `probe-same-user-late-mutation.json`: `mutationObserverStaleTitleAppearances=1`, exit 0.
2. Та же незавершённая мутация A, но после истечения сессии входит B. B уже на `/`; затем старый POST получает 401. Центральный `MutationCache.onError` не знает сессию инициатора, вызывает `expireSession` для нынешнего кеша и отправляет B на `/login?next=%2F`. `probe-old-mutation-401-after-b.json`: `userBeforeOldResponse=user-b`, `loggedOutAfterOldResponse=true`, exit 0; скриншот показывает форму входа.

Это одна отсутствующая гарантия жизненного цикла сессии с двумя последствиями. `user_id` различает A и B, но не два входа A. `QueryClient.clear()` не отменяет уже выполняющуюся mutation и её callbacks. Нужна проверка экземпляра/поколения сессии для успешных ответов, ошибок и иных клиентских side effects; старый 401 не завершает новый вход, старый 200 не показывается даже кратко. Регрессии должны охватывать обе последовательности и нормальные результаты текущей сессии.

Ручной вызов callback подменённого EventSource после его закрытия не принят как находка: возможность такой доставки настоящим браузером не доказана. Перестраивать SSE по этому искусственному probe не требуется; общая граница сессии при этом остаётся обязательной.

## 2. P2 — белый хвост разных размеров даёт нулевой цветовой diff без явного несовпадения

Место: `web/e2e/visual-compare.mjs:58–71,80–87,159–168`.

Объединённый canvas заполняется белым. Поэтому белые PNG 64×48 и 72×48 дают `changed=0`, хотя исходные размеры разные. Помимо независимого расчёта, точная текущая `compare()` извлечена из tracked файла и выполнена в Chromium без запуска harness: `changed=0` и для разной ширины 64×48/72×48, и для разной высоты 64×48/64×56, exit 0; сырые данные сохранены в `actual-compare-white-size.json`. Размеры присутствуют отдельными числовыми полями, но результат не выделяет несовпадение как таковое; self-check использует лишь красное изображение с красным дополнительным столбцом и не проверяет белый хвост. Это оставляет пробел в явно заданном критерии «разные размеры не дают ложного совпадения».

Решение архитектора: цветовой счётчик можно сохранить нулевым, но добавить явный результат несовпадения размеров, включить его в итоговую оценку равенства и отчёт. Самопроверка обязана различать белые PNG разных ширины/высоты, а также одинаковые и отличающиеся цветом PNG. Отсутствующие строки нельзя приравнивать к существующим только потому, что фон белый.

Дополнительно в том же visual harness синхронизировать **фазу полосок**, а не только этап карусели. Адресное измерение фактического DOM: продукт на этапе 1, hover/focus держат заполнение **0%**; у макета остаётся `seg1` CSS-анимация, при измерении заполнение **11,25%** (21,24 из 188,80 px). Значение зависит от длительности загрузки; утверждение PR про приблизительно 2% не подтверждено этим прогоном. Это условие получения снимков, не отдельный дефект карусели или вёрстки. Для сравнения остановить обе стороны на одной фазе и обновить описание PR по результату.
