## P2 — два перенаправления конкурируют за next

`OrderForm.tsx:176–177` вызывает `expireSession(queryClient)` и затем `navigate(/login?next=/orders/{id})`. Изменение `me` запускает `RequireAuth.tsx:26–28`, где адрес возврата вычисляется по прежнему маршруту `/`. Его `<Navigate>` может перезаписать адрес созданного заказа на `/login?next=%2F`.

Проверено на точном head:

- Полный настоящий Playwright: **24 PASS, 1 FAIL**; новый тест оформления PUT 401 упал с `no order next …/login?next=%2F`.
- Адресный настоящий повтор этого теста трижды: **1 PASS, 2 FAIL** с тем же адресом.
- Независимый Chromium с явно замоканным свежим `/me` 200, POST создания и PUT 401: **1 из 5** запусков оставил неправильный next после `response.finished()` и ещё 500 мс. Остальные проходили. Это гонка продуктовой навигации; успешный CI её не опровергает.

Вход уже остаётся видимым — эту часть не ломать. При неверном `next=/` существующий LoginPage направит после входа на главную вместо созданного заказа.

**Сначала уточни 07/09, затем исправляй код.** Локальные уточнения оркестратора пока не опубликованы; правило полностью здесь:

- Если заказ уже создан, `/orders/{id}` — адрес возврата при 401. Завершение сессии и auth gate не могут заменить его исходной главной `/` при любом порядке Query-уведомлений и эффектов React.
- У завершения сессии и перехода на вход должен быть согласованный источник адреса возврата. Выбери минимальное решение внутри клиента, сохраняющее очистку кеша и проверку поколения инициатора. Два независимых перенаправления, которые могут перезаписать next, не являются надёжным решением.
- После завершения переходов форма остаётся на `/login?next=/orders/{id}`; повторный вход открывает тот же заказ, без второго POST создания.
- Не лечить гонку `setTimeout`, дополнительной паузой теста или ожиданием «пока URL станет правильным», когда он может навсегда остаться неправильным. Не менять тест на допустимость `next=/`.
