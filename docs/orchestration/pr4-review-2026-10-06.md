## Подтверждённые замечания

### 1. P1 — разные вложения перезаписываются после нормализации имён

Код: `internal/worker/jobdir.go:75`, `:262`; `internal/worker/revise.go:140`.

Воспроизведение: HTTP-сервер отдаёт разные файлы `a:b.txt` и `a_b.txt` с корректными SHA. Два вызова `downloadInput` заканчиваются успешно, но на диске один `input/a_b.txt` с содержимым второго. `TASK.md` тоже ссылается на один путь. В доработке дополнительный дефект: файл сохраняется как `input/revision-2/a_b.txt`, а `REVISION-2.md` содержит `input/revision-2/a:b.txt`.

Ожидалось: оба файла сохранены под разными стабильными именами; каждый путь в промпте и Markdown указывает на свой существующий файл. Учитывать регистр Windows, имена папок, зарезервированные имена, конечные точки/пробелы. Проверки: `TestReviewInputMappingCollision`, `TestReviewRevisionMappedPath`.

### 2. P1 — лимит памяти трейса не действует

Код: `internal/worker/agents/run.go:255`, `internal/worker/agents/parser.go:72`; накопительные `steps` обоих парсеров.

Воспроизведение: 100 событий command_execution, каждое с 900 КиБ вывода, парсинг и немедленное извлечение каждой пачки из очереди. После GC очередь содержит 0 байт, парсер удерживает все 100 шагов, прирост heap — около 90 МиБ. `tailBytes` возвращает подстроку, сохраняющую исходную большую строку; парсер никогда не освобождает уже отправленные или отброшенные шаги. При отсутствии сети дополнительно одновременно удерживаются отправляемая пачка и новая очередь.

Ожидалось: общий удерживаемый трейс ограничен, отправленные/отброшенные шаги освобождены, хвосты копируются в собственные короткие строки. Проверка: `TestReviewTraceMemoryBound`.

### 3. P1 — обычный выход агента с живым дочерним процессом зависает

Код: `internal/worker/agents/run.go:189–192`, `:306`.

Воспроизведение на Windows: родитель запускает ребёнка на 20 секунд с унаследованными stdout/stderr и выходит с 0. `Run` не завершается: `cmd.Wait()` ждёт закрытия обоих pipes, а `group.Close()` находится после Wait. Ребёнок должен быть убит закрытием Job, но до закрытия Job исполнение не доходит. Отмена контекста разблокирует тест; без неё долго живущий ребёнок задержит этап до таймаута.

Ожидалось: выход родителя отслеживается независимо от EOF; после выхода закрывается Job, дети завершаются, хвост лога дочитывается, Run возвращается. Проверка: `TestReviewNormalExitClosesJob`.

### 4. P2 — подтверждённая отмена не запрещает commit снимка

Код: `internal/worker/snapshot.go:187–191`, проверки вокруг вызовов снимка в `internal/worker/job.go`.

Воспроизведение на живом сервере: прокси задерживает первый PUT снимка v1; клиент отменяет заказ; heartbeat получает `cancel:true`; прокси отпускает PUT. Воркер продолжает загрузку и отправляет `POST .../snapshot/v1/commit` → 204. После этого finish переводит заказ в canceled, current_version остаётся 0: клиент не получает ошибочный done, но commit после известной отмены всё равно выполнен. В БД/хранилище появляются лишние результаты отменённого снимка.

Ожидалось: после подтверждённой отмены нет commit и finish ok; обработка снимка прекращается, отправляется finish canceled. Проверка должна охватывать draft и v1/vN, в том числе повтор сетевого запроса после отмены.

### 5. P2 — revise без сессии получает неполные инструкции

Код: `internal/worker/stage.go:304–308`, `prompts/revise.md:1`.

Воспроизведение: `buildPrompt("revise", "continue", false)`, `answer` без сессии и `start` с attempt=1. Возвращается короткий revise без общего блока и без «Предыдущая попытка не завершилась…»: шаблон не использует Retry. Текущий TestBuildPrompt проверяет только draft.

Ожидалось: полные инструкции текущего этапа и сведения о задании; блок повтора и ответ клиента по правилам. Обычная доработка с существующей сессией может оставаться короткой. Проверка: `TestReviewReviseWithoutSession`; нужна таблица всех этапов и действий. Нормативное уточнение внесено локально в 05 и 06.

### 6. P2 — результат инструмента не с чем связать

Код: `internal/worker/agents/claude.go:132–161`.

Воспроизведение: tool_use с id `call-123`, затем соответствующий tool_result. У результата есть `payload.tool_use_id`, а у исходного command/file/tool/web шага id вызова отсутствует. После отправки в трейс идентификатор вызова теряется; два одинаковых или параллельных вызова нельзя надёжно различить.

Ожидалось: один и тот же id хранится на исходном вызове и отдельном результате. Проверка: `TestReviewToolResultLink`; также нужны два одинаковых вызова с результатами в обратном порядке и паузой между пачками.

### 7. P2 — существующий REVISION-N.md скрывает пропавшие вырезки

Код: `internal/worker/revise.go:28–30`.

Воспроизведение: подготовить доработку, удалить только remarks/1.png, оставив Markdown и страницу предыдущего снимка; повторить prepareRevision. Возвращается успех, вырезка не восстанавливается. Markdown продолжает ссылаться на отсутствующий файл.

Ожидалось: проверять комплект, восстанавливать недостающую вырезку, идемпотентно загружать её и публиковать согласованный Markdown. Проверка: `TestReviewRevisionMissingCrop`.

### 8. P2 — в новых fixtures сохранены запрещённые идентификаторы моделей

Код: `internal/worker/agents/testdata/claude_real_verify.jsonl:1`, `claude_real_resume.jsonl:1` и последующие события.

Ожидалось: нейтральные заполнители при сохранении структуры JSONL и проверяемых событий. Проверить также экранированные вложенные строки. Новые реальные логи перед коммитом проверяются на идентификаторы моделей и личные данные.
