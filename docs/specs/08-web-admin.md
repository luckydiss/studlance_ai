# 08. Пульт админа (`web/admin`)

Плотный рабочий интерфейс; ориентир — `design/mockups/AdminReview.dc.html`. Тот же шрифт и токены, что в кабинете, но **шапка тёмная** (`#15171A`, текст белый), чтобы пульт не путался с кабинетом. Базовый путь `/admin`. Доступ только роли `admin`.

Шапка: «studlance · пульт», ссылки «Заказы», «Клиенты», «Воркеры»; справа почта и «Выйти».

## Доступ, сессия и ошибки

- `/admin` открывает `/admin/jobs`; прямые адреса карточки, клиентов и воркеров работают после перезагрузки. До проверки `me.role === admin` приватный интерфейс не показывается и admin-запросы не запускаются. API самостоятельно проверяет роль; клиент не получает admin-данные даже при прямом HTTP-запросе.
- Неавторизованный пользователь направляется на общий `/login?next=<локальный адрес пульта>`; после входа админ возвращается туда. Для проверенного локального `next`, чей pathname равен `/admin` или начинается с `/admin/`, вход админа делает полную браузерную навигацию; обычные пути кабинета сохраняют SPA-навигацию. Не искать admin-маршрут в роутере кабинета. Авторизованный клиент при открытии пульта направляется на `/login`; существующий вход клиента может штатно вернуть его в кабинет `/`, но циклического перехода обратно в пульт нет. 403 не считается истечением действующей клиентской сессии. `next` проверяется как локальный адрес, клиентская роль не перенаправляется в пульт.
- 401 текущей сессии прекращает admin-запросы, polling и SSE, очищает приватный кеш и направляет на вход с адресом возврата. Ключи admin-кеша отделены от клиентских и включают пользователя. Запросы, мутации и подписки захватывают экземпляр сессии при запуске: поздний ответ или событие прежнего экземпляра (включая повторный вход того же админа) не меняет кеш, форму, маршрут и toast новой сессии. При выходе подписки и таймеры закрываются.
- Сетевая ошибка оставляет доступный повтор, 404 карточки показывает «Заказ не найден» без прежних данных, 409 действия показывает ошибку и обновляет состояние заказа. Действие блокируется на время собственного запроса; успех подтверждается серверным ответом, а не только скрытием кнопки.

## `/admin/jobs` — заказы

Таблица, новые сверху, обновление раз в 10 с: название · клиент (почта) · статус и этап (`running · verify`) · версия · попытка · воркер · создан · обновлён · флаг «требует внимания» (оранжевая точка). Фильтры над таблицей: статус (все / в работе / ждут ответа / готово / сбой / отменены), «только требующие внимания», поиск по названию и почте. Клик — разбор заказа.

Фильтры применяются совместно и сохраняются в URL при переходе в карточку и обратно. «В работе» включает `queued`, `running`, `revising`; «ждут ответа» — `needs_input`; остальные соответствуют `done`, `failed`, `canceled`. «Все» включает `uploading`. В URL допускается фильтр `client=<id>` после перехода из таблицы клиентов; в текущем API нет `client_id`, поэтому такой фильтр применяется к `job.client.id`, без выдуманного серверного параметра. При поиске и фильтрах нет заказов — отдельное пустое состояние, не ошибка.

## `/admin/jobs/:id` — разбор заказа

**Шапка заказа:** название, клиент, статус и этап, версия, воркер, `lease` (истекает через N с), попытка. Действия: «Ответить за клиента» (если `needs_input`: поле ответа), «Повторить» (если `failed`), «Отменить» (если можно), «Снять флаг внимания». Ошибка (`error`) — красной строкой под шапкой.

**Три колонки:**

1. **Трейс (слева, 380 px)** — запуски агентов по порядку: «codex · черновик · попытка 1», «claude · проверка», «claude · доработка 2»; у каждого — время начала, длительность, исход, токены и стоимость, ссылка «сырой лог». Внутри — шаги live (SSE `steps`): время `14:03:21`, иконка типа (сообщение, рассуждение, команда, файл, веб, инструмент, ошибка), `summary` одной строкой; клик раскрывает `payload` (команда и вывод моноширинным шрифтом, путь файла, текст). Фильтр по типу шагов. Автопрокрутка вниз, пока пользователь не прокрутил вверх.
2. **Листы (центр)** — переключатель «Черновик / Версия 1 / Версия 2…», список документов и просмотр страниц как в кабинете; переключатель «Показать правки» рисует `changed_boxes` полупрозрачными оранжевыми рамками `#E8590C`; на версии, к которой были замечания клиента, — их рамки и тексты.
3. **Справа (320 px)** — итог проверки из `verification` («Найдено 7 · исправлено 7», список `remaining` с важностью), доработки клиента (комментарий, замечания со ссылками на листы, приложенные файлы), исходные файлы заказа (скачать), события заказа лентой, заметки админа (поле «Заметка» + список).

### История и live-трейс

- `snapshot`/`job` несут `AdminJobDetail`, `steps` — `{run_id, steps}`. Деталь не заменяет историю шагов: для каждого run история загружается через `GET …/runs/{run_id}/steps?after_seq=` (до 500 за ответ), с продолжением до конца. Уже завершённый заказ с 2 000 шагов должен быть доступен целиком после открытия и перезагрузки.
- История и SSE объединяются по `(run_id, seq)` в порядке `seq`: дубликаты не показываются; live-пачка во время первой загрузки не позволяет пропустить более раннюю историю. После обрыва подключение восстанавливается с паузами 1→2→5→10 с, новый snapshot обновляет заказ, пропущенные шаги добираются HTTP-запросами. При смене заказа старые ответы и события не попадают в новую карточку; запросы, подписка и таймеры закрываются.
- Payload раскрывается по требованию и отображается текстом, без исполнения HTML из summary/команд/вывода. Отсутствующие tokens/cost/outcome показываются как отсутствие данных, не выдуманный ноль. На 2 000 шагах нельзя монтировать все раскрытые payload; использовать виртуализацию или ограниченный DOM с дозагрузкой. Фильтр типов не теряет уже загруженные шаги. Автопрокрутка прекращается после ручной прокрутки вверх и возобновляется по явному действию или возврату вниз.

### Листы и действия

Черновик и каждая готовая версия имеют отдельные документы, страницы и URL ресурсов из admin-пространства. Переключение не оставляет лист предыдущей версии во время загрузки; отсутствие черновика/страниц/проверки отображается явно. Рамки `changed_boxes` и замечаний пересчитываются к фактическому масштабу листа; ссылка замечания выбирает правильный документ, страницу и версию, к которой оно относится. Пути файлов сохраняются точно (включая пробелы и папки), кодируются одним URL-сегментом по контракту [04](04-api.md). Документы не подменяются макетными листами.

У текущего `verification.remaining` есть `severity` и `description`, но нет координат листа: такие пункты отображаются списком, привязка к документу не выдумывается. Навигация к листу обязательна для клиентских замечаний с настоящими `document_id`/`page`.

**Исходники и вложения:** в PR 6 добавить описанные в [04](04-api.md) `AdminInputFile {path,size,revision}` и admin GET `/jobs/{id}/input/{path}`. `revision=0` показывается в исходниках, `revision=n` — среди файлов доработки n; связь берётся из `files.version`, а не префикса пути. Это позволяет отличить исходник с именем `input/revision-2/…` от настоящего вложения. Скачивание идёт по точному пути из admin-списка, с admin-сессией, без воркерского токена/lease; выдаётся только input-файл этого заказа. Клиентский/worker-контракт и хранилище не переделывать.

Ответ, повтор, отмена, снятие флага и заметка используют существующие admin POST-эндпоинты. Доступность действий определяется статусом/флагами сервера; повтор допустим только при `failed`, ответ — при `needs_input`. Заметка после успешной записи сохраняется после перезагрузки. Отмена в работе ожидает фактического серверного `canceled`, а не немедленной локальной имитации. Действия админа не вводят этап одобрения готовой работы.

## `/admin/clients`

Таблица: почта, имя, всего заказов, последний заказ. Клик — список заказов клиента (тот же экран заказов с фильтром по клиенту).

## `/admin/workers`

Таблица: имя, онлайн (зелёная/серая точка, «был 2 мин назад»), возможности (чипы), версии codex/claude из `info`, текущий заказ (ссылка).

## Тесты (Playwright, на фейковых агентах)

Админ видит заказ клиента, live-шаги трейса появляются во время работы, переключение «Черновик / Версия 1», «Показать правки», ответ за клиента на вопрос, «Повторить» после `#fail-verify`, клиент не может открыть `/admin` (редирект на `/login`).

Дополнительно: прямой адрес и возврат после входа админа; отсутствие admin-запросов до проверки роли; отсутствие циклов для клиента; совместные фильтры и переход из клиентов по точному id; отмена, флаг и сохранённая заметка; воркер онлайн/офлайн и ссылка на текущий заказ; SSE disconnect/reconnect без потерь и дублей; 2 000 шагов (несколько HTTP-пачек, прокрутка к последнему, раскрытие и фильтр типов), пауза автопрокрутки; 401/403/404/409/сеть; поздние данные прежнего заказа и сессии не появляются в новой карточке. Для проверки успешного admin retry использовать `#fail-verify-twice`: после двух сбоев и ручного повтора заказ достигает `done`; постоянный `#fail-verify` остаётся сценарием повторного сбоя, успех для него не подделывать.
