# План разработки MVP

Порядок выбран так, чтобы как можно раньше прогнать схему «сайт ↔ воркер» целиком, сначала с фейковыми агентами, потом с настоящими. Архитектура — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Этап 0. Каркас

- Go-модуль, `cmd/server`, `cmd/worker`, `internal/…`.
- `deploy/docker-compose.yml`: Postgres, MinIO, Caddy, API.
- Миграции `goose`, черновик `api/openapi.yaml`, генерация сервера (`oapi-codegen`) и запросов (`sqlc`).
- CI: `golangci-lint`, `go test`.

**Готово, когда:** `docker compose up` поднимает всё, `GET /healthz` отвечает, миграции применились.

## Этап 1. Очередь и воркер без настоящих агентов

- Пользователи и сессии: `server user create`, вход/выход, роли `client` и `admin`, пространства `/api/client`, `/api/admin`, `/api/worker`.
- Заказы: создание, presigned-загрузка файлов, submit, отмена, повтор, ответ на вопрос, доработки и версии.
- Воркер: регистрация, возможности, claim (long-poll), lease, heartbeat, fencing, finish.
- Рабочая папка, скачивание `input/`, снимки `out/` в S3.
- Фейковые `codex` и `claude` (скрипты, которые пишут JSONL и файлы, задают вопрос, падают, зависают).
- E2E-тесты на testcontainers: обычный заказ, вопрос → ответ, доработка → версия 2, отмена, сбой → авто-повтор, смерть воркера и продолжение, запись от старого воркера отклоняется, клиент не видит чужой заказ.

**Готово, когда:** заказ проходит все статусы через API с фейковыми агентами, тесты зелёные.

## Этап 2. Настоящие агенты

- Запуск `codex exec` и `claude -p` по контракту (stdin, resume, id сессий в БД).
- Парсеры JSONL обоих CLI → шаги трейса; сырые логи в S3; токены и стоимость в `agent_runs`.
- Windows Job Objects, таймауты этапов, зачистка КОМПАС/Office.
- Определение возможностей (PATH, ProgID в реестре).
- Шаблоны промптов в `prompts/`.
- Превью листов: PDF из `preview/` → PNG страниц и мини-копии, попиксельное сравнение черновика и финала.

**Готово, когда:** реальная работа с КОМПАСом проходит на ПК от загрузки до финального комплекта.

## Этап 3. Фронты

- `web/shared`, `web/client`, `web/admin` по [ARCHITECTURE.md §13](ARCHITECTURE.md#13-фронт) и согласованному дизайну.
- Кабинет: заказы, новый заказ с примерами комплектов, комплект на столе с превью листов, сворачиваемое окошко статуса, ответ на вопрос, замечания на листах и доработка, скачивание.
- Пульт: все заказы, разбор по листам (трейс, черновик и финал с подсветкой правок, ведомость замечаний), клиенты, воркеры.

**Готово, когда:** тестовый клиент проходит весь цикл в кабинете (включая доработку), а админ видит и разбирает его в пульте.

## Этап 4. Наблюдаемость и устойчивость

- `/metrics`, экран метрик, логи `slog`.
- Инструкция по установке воркера на Windows (отдельная учётная запись).
- Прогон сценариев сбоя на живом ПК: перезагрузка, обрыв сети, отмена посреди КОМПАСа.

## Этап 5. Обкатка

- 5–10 реальных работ разных типов (отчёт, расчёты в Excel, чертежи).
- Правка промптов по итогам трейсов, список того, что мешает качеству.
