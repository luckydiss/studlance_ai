# План разработки MVP

Цель MVP — **проверить, что идея работает**: codex делает черновик комплекта, claude проверяет и доводит до финала, доработка по замечаниям даёт новую версию, и всё это запускается из сайта. Всё на одном ПК, **без Docker** и без отдельных серверов БД.

Архитектура для прода — в [ARCHITECTURE.md](ARCHITECTURE.md), дизайн — в [DESIGN.md](DESIGN.md). MVP — их урезанная версия: тот же протокол «воркер сам забирает заказ по HTTP», та же папка заказа, промпты и статусы, но хранилища простые и спрятаны за интерфейсами, которые в проде заменяются на Postgres и S3.

## Итог: что получится

| Часть | Как устроено в MVP |
|---|---|
| `studlance-server.exe` | API + сайт (кабинет и пульт вшиты в бинарник) + SQLite + файлы в папке `data\` |
| `studlance-worker.exe` | забирает заказы по HTTP, гоняет codex и claude, отдаёт трейс и файлы; умеет работать и без сервера (`run`) |
| Кабинет `/` | вход, мои заказы, новый заказ, страница заказа: статус, вопрос, просмотр листов, замечания на листах, версии, скачивание |
| Пульт `/admin` | все заказы, трейс агентов, черновик и финал, ответ за клиента, повтор, отмена |

## Отличия MVP от прода

| | MVP | Прод |
|---|---|---|
| Запуск | два exe на ПК | сервер в контейнерах, воркеры на VM |
| База | SQLite, один файл (`modernc.org/sqlite`, без CGO), режим WAL | PostgreSQL |
| Файлы | папка на диске, отдача и приём через сервер | S3, presigned URL |
| Live-статусы | SSE из памяти сервера | SSE + `LISTEN/NOTIFY` |
| Сайт | сервер сам отдаёт фронты (`go:embed`) | Caddy / CDN |
| Очередь | та же логика claim, lease, heartbeat, fencing; выдача в транзакции `BEGIN IMMEDIATE` | Postgres, `FOR UPDATE SKIP LOCKED` |

```

internal/blobs/             интерфейс файлов + реализация «папка на диске»
internal/auth/              пароли (Argon2id), сессии, middleware ролей, лимит попыток входа
internal/jobs/              заказы, статусы, версии, доработки, вопросы и ответы

internal/live/              SSE-хаб в памяти
```

## Этап 1. Проверка идеи без сайта

Самый короткий путь к ответу «работает ли»: прогнать настоящие агенты на настоящих заданиях из командной строки.

### Бэкенд (воркер)

- **Команды:**
  - `studlance-worker run <папка> [--input <файлы>] [--prompt "запрос"]` — весь конвейер первой версии;
  - `studlance-worker answer <папка> "ответ"` — продолжить после вопроса агента;
  - `studlance-worker revise <папка> "замечания" [--files …]` — доработка, версия N+1;
  - `studlance-worker fixture <путь к fixtures/имя> <папка>` — собрать папку заказа из тестового заказа приватного репозитория.
- **Папка заказа** по [контракту](ARCHITECTURE.md#рабочая-папка): `input/`, `TASK.md`, `out/`, `preview/`, `manifest.json`, `SUMMARY.md`, `QUESTIONS.md`, `VERIFICATION.md`, `verification.json`, `REVISION-N.md`; служебное в `.studlance/` (`state.json`: этап, id сессий, версии).
- **Конвейер:** `draft` (codex) → снимок черновика в `.studlance/draft/` → `verify` (claude) → снимок `.studlance/v1/`; при `QUESTIONS.md` — остановка со статусом «нужен ответ».
- **Промпты** `prompts/draft.md`, `verify.md`, `revise.md` по [сути из архитектуры](ARCHITECTURE.md#что-говорим-агентам-суть-промптов), подстановка списка файлов, запроса, замечаний.
- **Запуск агентов:** промпт через stdin; новая сессия и `resume` по [таблице флагов](ARCHITECTURE.md#запуск-cli); `thread_id` codex из `thread.started`, uuid сессии claude генерирует воркер; всё сразу в `state.json`.
- **Разбор логов:**
  - codex `--json`: `thread.started`, `item.*` (сообщение, рассуждение, команда, изменение файла, веб-поиск), `turn.completed` с usage;
  - claude `stream-json`: `system/init` (сессия), `assistant` (текст, `tool_use`), `user` (`tool_result`), `result` (usage, стоимость, длительность);
  - неизвестные события не ломают разбор; сырой JSONL пишется целиком в `.studlance/logs/`.
- **Отчёт прогона** `.studlance/report.md`: время каждого этапа, токены и стоимость, что агенты делали (кратко), состав комплекта из `manifest.json`, итог проверки из `verification.json`.
- **Windows:** дерево процессов агента в Job Object (`KILL_ON_JOB_CLOSE`), таймаут этапа (по умолчанию 3 ч), Ctrl+C — аккуратная остановка; после этапа закрываются `KOMPAS*.exe`, `WINWORD.EXE`, `EXCEL.EXE`, запущенные во время этапа.
- **Фейковые агенты** (`cmd/fakeagent`): выдают правдоподобный JSONL каждого CLI, пишут файлы комплекта и `manifest.json`; флаги: задать вопрос, упасть, зависнуть, не положить PDF.

### Тесты и CI

- Юнит-тесты разбора JSONL на записанных логах обоих CLI.
- Сквозные тесты конвейера на фейковых агентах: первая версия, вопрос → ответ, доработка → v2, падение агента, таймаут.
- GitHub Actions: `golangci-lint`, `go test` на Linux, сборка `studlance-worker.exe` под Windows как артефакт.

### Приёмка

На вашем ПК три заказа из `fixtures/` разных типов — записка с Excel, чертежи в КОМПАСе, программа со скриншотами — проходят черновик → проверку → финал, одна доработка даёт версию 2. По `report.md` и сравнению с эталонами из `reference/` пишем короткий вывод: работает ли схема, сколько времени и токенов, что мешает качеству.

## Этап 2. Сервер, очередь и воркер по HTTP

### Бэкенд

- **Сервер** `studlance-server.exe serve` — один процесс: API, сайт, SQLite, папка файлов. Конфиг: адрес, путь к `data\`, срок сессии.
- **Миграции** (goose, вшиты, применяются при старте) — таблицы из [§10](ARCHITECTURE.md#10-данные-postgres) в варианте для SQLite: `users`, `sessions`, `jobs`, `revisions`, `revision_remarks`, `files`, `pages`, `workers`, `agent_runs`, `trace_steps`, `events`, `job_notes`.
- **Служебные команды:** `user create --email --role client|admin --name`, `worker token --name`.
- **Вход:** `POST /api/auth/login|logout`, `GET /api/auth/me`; Argon2id, сессия в httpOnly-cookie (хэш токена в БД), проверка `Origin` на изменяющих запросах, лимит попыток.
- **API клиента** `/api/client` (только свои заказы, чужой → 404):
  - `POST /jobs` (запрос) → `PUT /jobs/{id}/files/{path}` (загрузка файлов и папок с относительными путями) → `POST /jobs/{id}/submit`;
  - `GET /jobs`, `GET /jobs/{id}` (статус для клиента, вопрос, версии, состав комплекта);
  - `GET /jobs/{id}/stream` — SSE, только статусы и вопрос;
  - `POST /jobs/{id}/answer`, `POST /jobs/{id}/cancel`;
  - `POST /jobs/{id}/revisions` — комментарий + замечания (документ, страница, область x, y, w, h в долях листа, текст) + файлы;
  - `GET /jobs/{id}/versions/{v}/files/{path}`, `GET /jobs/{id}/versions/{v}/bundle.zip`, `GET /jobs/{id}/versions/{v}/pages`.
- **API пульта** `/api/admin`: все заказы с фильтрами, карточка заказа, трейс (`agent_runs` + `trace_steps`), SSE со всем, версии и черновик, ответ за клиента, повтор, отмена, заметки.
- **API воркера** `/api/worker` (токен воркера): `register` (возможности), `claim` (long-poll до 25 с), `jobs/{id}/heartbeat` (продлевает lease, отдаёт флаг отмены), `jobs/{id}/input` (список и скачивание файлов), `jobs/{id}/trace` (пачки шагов, идемпотентно по `(agent_run_id, seq)`), `jobs/{id}/state` (этап, id сессий), `jobs/{id}/question`, `jobs/{id}/files` (загрузка снимков и логов), `jobs/{id}/finish`. Каждая запись несёт `lease_epoch`, устаревшая отклоняется.
- **Очередь:** выдача по [§6](ARCHITECTURE.md#6-очередь-leases-отказоустойчивость) в транзакции SQLite; lease 60 с, heartbeat 15 с; заказ закреплён за воркером; сбой этапа → один авто-повтор → `failed` + `needs_attention`; таймаут этапа.
- **Статусы для клиента** — по [таблице](ARCHITECTURE.md#что-видит-клиент); название заказа — из `SUMMARY.md` после черновика.
- **Воркер** `studlance-worker serve`: регистрация, цикл claim → скачать `input/` → тот же конвейер, что на этапе 1 → трейс пачками раз в секунду → снимки и логи на сервер → finish; heartbeat в фоне, отмена убивает Job Object; после перезапуска забирает свой заказ и продолжает этап через `resume`.
- **Live:** SSE-хаб в памяти, события из обработчиков записи.

### Фронтенд

- **Каркас** `web/` на pnpm: React + Vite + TypeScript, TanStack Query, роутер, Biome; `web/shared` — тема (цвета, шрифт Golos Text из DESIGN.md), базовые компоненты, API-клиент из `openapi.yaml`, хук SSE, авторизация. Сборка складывается в `internal/web/dist` и вшивается в сервер.
- **Кабинет:**
  - `/login`;
  - `/` — мои заказы: название, статус простыми словами, дата, «Новый заказ»;
  - `/new` — по макету: «Что нужно сделать?», поле запроса, загрузка файлов и папок (перетаскивание, прогресс), «Оформить заказ»; ниже стопка листов реальных работ и блок «Как это работает» (сторис из пяти этапов);
  - `/orders/:id` — статус, сворачиваемое окошко статуса с шагами простыми словами, вопрос и поле ответа, состав комплекта (пока идёт работа — заготовки с названиями документов), скачивание файлов и архива, переключатель версий, «Нужна доработка» с комментарием и файлами.
- **Пульт:** `/admin/jobs` (список, фильтры, флаг «требует внимания»), `/admin/jobs/:id` (live-трейс по этапам, итог проверки, события, ответ за клиента, повтор, отмена, заметки).

### Тесты

- Go: сквозные тесты сервер + воркер + фейковые агенты на временной SQLite: заказ до «Готово», вопрос → ответ, доработка → v2, отмена во время работы, сбой → авто-повтор → `failed`, перезапуск воркера → тот же этап, запись со старым `lease_epoch` отклоняется, повторная пачка трейса не дублируется, клиент не видит чужой заказ.
- Браузерные тесты (Playwright) на фейковых агентах: вход, новый заказ с файлами, ответ на вопрос, скачивание, доработка, пульт видит трейс.
- CI: плюс сборка фронтов, Biome, Playwright.

### Приёмка

На ПК запущены оба exe; тестовый клиент в браузере проходит весь цикл на настоящих агентах — загрузка, вопрос и ответ, готовый комплект, доработка, версия 2; админ видит трейс этого заказа в пульте.

## Этап 3. Работа на листах

### Бэкенд

- **Превью:** после каждого снимка воркер рендерит PDF из `preview/` в PNG страниц и мини-копии (`pdftoppm` поставляется рядом с воркером), загружает на сервер, записывает в `pages`. Если агент не положил PDF — конвертирует docx/xlsx через Word/Excel (COM) или LibreOffice.
- **Сравнение версий:** попиксельное сравнение страниц финала с черновиком и v(N) с v(N−1), рамки изменённых областей в `pages.changed_boxes`.
- **Замечания с местом:** при доработке воркер вырезает выделенные области из картинок страниц в `input/revision-N/remarks/`, в `REVISION-N.md` — документ, страница, область, текст и ссылка на вырезку.
- API: страницы версии с размерами, мини-копии, рамки изменений.

### Фронтенд

- **Кабинет `/orders/:id` — комплект на столе:** документы комплекта с мини-копиями, просмотр листов с листанием («стр. 16 из 32»), переключатель версий; режим замечаний — выделение области на листе рамкой и текст замечания, список замечаний, «Отправить на доработку».
- **Пульт `/admin/jobs/:id` — разбор по листам:** черновик и финал рядом, подсветка изменённых мест, ведомость замечаний claude из `verification.json`, замечания клиента на листах.

### Приёмка

Клиент выделяет место на листе, отправляет замечание, получает версию 2 и видит, что поправлено; в пульте видна разница черновика и финала.

## Этап 4. Доводка MVP

- Обкатка на 10–15 работах из `fixtures/` разных типов, правка промптов по трейсам.
- Экран метрик в пульте: длительность этапов, токены и стоимость, доли доработок и сбоев.
- Сценарии сбоев на живом ПК: перезагрузка во время работы, обрыв сети, отмена посреди КОМПАСа.
- Резервная копия: `studlance-server backup` — копия SQLite и папки файлов.
- Инструкция по установке и запуску на ПК.

## После MVP

- Postgres и S3 вместо SQLite и папки, docker compose для сервера, пул воркеров на VM — по [§15](ARCHITECTURE.md#15-горизонтальное-масштабирование-и-путь-в-прод).
- Полный пульт: клиенты, воркеры.
- Регистрация, оплата, уведомления.

## Как ведём работу

- Каждый этап — отдельный PR с инструкцией «как проверить на ПК»; крупный этап можно разбить на 2–3 PR (бэкенд, фронтенд).
- Код и тесты на фейковых агентах я гоняю в облаке; настоящие codex, claude, КОМПАС и Office проверяются на вашем ПК.
- По умолчанию: Go 1.24, Node 22 и pnpm; бинарники собираются под Windows в CI.
