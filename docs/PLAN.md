# План разработки MVP

Цель MVP — проверить, что схема работает целиком: студент на сайте загружает задание и пишет запрос, воркер на ПК делает работу через codex и claude, готовый комплект появляется в кабинете, доработка даёт новую версию. Архитектура — в [ARCHITECTURE.md](ARCHITECTURE.md), дизайн — в [DESIGN.md](DESIGN.md).

Порядок выбран так, чтобы как можно раньше прогнать сквозной путь «сайт ↔ воркер»: сначала с фейковыми агентами (всё проверяется автоматически, на любой машине), потом с настоящими (на ПК с Windows и КОМПАСом).

## Как ведём работу

- Каждый этап — отдельная ветка и PR. В PR: что сделано, как проверить, что осталось.
- Всё, что можно проверить без Windows, проверяется автоматически: юнит-тесты, e2e на фейковых агентах, линтеры. Это прогоняю я в облаке и CI на GitHub.
- Windows-часть (Job Objects, реестр, КОМПАС, Office, настоящие codex и claude) проверяется на вашем ПК по короткой инструкции в PR.
- Приёмка настоящих агентов — на тестовых заказах из приватного репозитория (`fixtures/`, 49 работ с эталонами).

## Решения по умолчанию

Если не возразите, берём так:

| Что | Решение |
|---|---|
| Go | 1.24, модуль `github.com/luckydiss/studlance_ai` |
| Фронты | Node 22, pnpm workspaces |
| БД, файлы, вход | PostgreSQL 16, MinIO, Caddy 2 — в docker compose |
| Сервер на ПК | Docker Desktop (WSL2), сайт на `http://localhost` |
| Воркер на ПК | `worker.exe` нативно, под отдельной учётной записью Windows |
| Пользователи | админ и один тестовый клиент, создаются командой `server user create` |
| CI | GitHub Actions: линтеры, тесты Go с Postgres и MinIO, сборка фронтов, сборка `worker.exe` |

## Этап 0. Каркас

- Go-модуль, `cmd/server`, `cmd/worker`, `internal/…` по [структуре репозитория](ARCHITECTURE.md#17-структура-репозитория).
- Конфиг через переменные окружения (сервер) и `worker.toml` (воркер), `log/slog` в JSON.
- `server migrate` на `goose`, миграции встроены в бинарник, применяются под advisory lock.
- Первая миграция: все таблицы из [§10](ARCHITECTURE.md#10-данные-postgres).
- `api/openapi.yaml` — каркас со всеми пространствами, генерация сервера (`oapi-codegen`) и запросов (`sqlc`) через `make generate`.
- `deploy/docker-compose.yml`: Postgres, MinIO (с бакетом), API, Caddy; `deploy/Caddyfile`.
- `GET /healthz` (проверяет Postgres и MinIO), `GET /metrics`.
- `Makefile`: `generate`, `lint`, `test`, `up`, `worker-windows`.
- CI: `golangci-lint`, `go test`, проверка, что сгенерированный код не устарел.

**Готово, когда:** `docker compose up` поднимает всё, `/healthz` отвечает 200, миграции применились, CI зелёный.

## Этап 1. Бэкенд, очередь и воркер на фейковых агентах

**1.1 Пользователи и вход**
- `server user create --email --role --name`, пароль Argon2id.
- `POST /api/auth/login|logout`, `GET /api/auth/me`; сессии в БД, httpOnly-cookie, проверка `Origin`, ограничение попыток входа.
- Middleware ролей для `/api/client` и `/api/admin`.

**1.2 Заказы со стороны клиента**
- Создание заказа: запрос + список файлов (с относительными путями, папки тоже) → presigned PUT в MinIO.
- `submit` (проверка, что файлы на месте) → `queued`.
- Список и карточка заказа, отмена, ответ на вопрос.
- Доработка: комментарий + замечания с местом на листе (документ, страница, x, y, текст) + файлы → `queued`, `stage = revise`.
- Версии результата, файлы версии, страницы превью, `bundle.zip`.
- Все запросы строятся с `user_id` из сессии; чужой заказ — 404.

**1.3 Очередь и API воркера**
- `server worker token --name`, токен хранится хэшем.
- `register` (возможности), `claim` long-poll с выдачей из [§6](ARCHITECTURE.md#6-очередь-leases-отказоустойчивость), lease 60 с, heartbeat 15 с с флагом отмены, fencing по `lease_epoch` на каждой записи.
- Приём трейса пачками (идемпотентно по `(agent_run_id, seq)`), presign для файлов воркера, сохранение состояния (`stage`, id сессий), `finish` с итогом.
- Сбой этапа → один авто-повтор → `failed` + `needs_attention`; таймаут этапа.

**1.4 Live-обновления**
- `LISTEN/NOTIFY` → SSE-хаб: клиенту только статусы и вопрос, админу всё (статусы, шаги трейса).

**1.5 Воркер (общая часть, работает и на Linux)**
- Главный цикл: claim → рабочая папка → скачивание `input/` → этап по `stage` → снимок `out/` → finish.
- Запуск агента как процесса с промптом в stdin, чтение JSONL, разбор в шаги трейса, сырой лог в S3.
- Чтение `manifest.json`, `SUMMARY.md`, `QUESTIONS.md`, `verification.json`.
- Возобновление после перезапуска: свой заказ, тот же этап, `resume` сессии.
- **Фейковые codex и claude**: маленькая Go-программа, которая пишет правдоподобный JSONL и файлы комплекта (docx, xlsx, PDF для превью) и по флагам задаёт вопрос, падает, зависает.

**1.6 Превью листов**
- PDF из `preview/` → PNG страниц и мини-копии через `pdftoppm`, загрузка в S3, запись в `pages`.
- Для финала — попиксельное сравнение с черновиком и рамки изменений.

**1.7 E2E-тесты** (Postgres и MinIO в тестах, воркер с фейковыми агентами):
обычный заказ до «Готово» · вопрос → ответ → продолжение · доработка → версия 2 · отмена во время работы · сбой → авто-повтор → `failed` · убили воркер → перезапуск → тот же этап · запись со старым `lease_epoch` отклоняется · клиент не видит чужой заказ · повторная пачка трейса не дублируется.

**Готово, когда:** заказ проходит все статусы через API с фейковыми агентами, все e2e зелёные.

## Этап 2. Настоящие агенты на Windows

- Запуск `codex exec` и `claude -p` по [контракту](ARCHITECTURE.md#запуск-cli): новая сессия и `resume`, `thread_id` и uuid сессии сразу в БД.
- Парсеры JSONL обоих CLI → шаги трейса (сообщение, команда, файл, веб-поиск, прочее); токены и стоимость в `agent_runs`.
- Шаблоны промптов `prompts/draft.md`, `verify.md`, `revise.md`, версия шаблонов пишется в заказ.
- Windows Job Objects: при отмене или таймауте убивается всё дерево процессов агента; затем закрываются КОМПАС, Word, Excel.
- Возможности: `codex`, `claude` в PATH; `kompas`, `word`, `excel` по ProgID в реестре; `python`, `browser` и прочее; ручные `extra`/`disable` в конфиге.
- Сборка `worker.exe` с `pdftoppm` рядом, `worker.toml` с примером.
- Инструкция «как поставить воркер на ПК»: учётная запись, установка, вход codex и claude, запуск.

**Готово, когда:** на вашем ПК 3 тестовых заказа из `fixtures/` (записка + Excel, чертежи в КОМПАСе, программа со скриншотами) проходят от загрузки до финального комплекта, а доработка одного из них даёт версию 2.

## Этап 3. Фронты

Общее: `web/shared` — тема, UI-компоненты, TS-клиент из `openapi.yaml`, авторизация, подписка на SSE.

**Кабинет клиента** (`web/client`) по утверждённому макету:
- `/login`.
- `/` — мои заказы: название, статус простыми словами, дата, «Новый заказ».
- `/new` — «Что нужно сделать?»: поле запроса, загрузка файлов и папок (drag-and-drop, прогресс); ниже стопка листов из выполненных работ разных типов и блок «Как это работает» — карусель из пяти этапов.
- `/orders/:id` — комплект на столе: пока идёт работа — заготовки листов с названиями документов; когда готово — превью страниц, просмотр с листанием, переключатель версий, «Скачать всё»; метки-замечания прямо на листе и «Отправить на доработку»; сворачиваемое окошко статуса с шагами и вопросом, если он есть.

**Пульт админа** (`web/admin`):
- `/admin/jobs` — все заказы, фильтры, флаг «требует внимания».
- `/admin/jobs/:id` — разбор по листам: live-трейс по этапам, превью «черновик / финал» с подсветкой правок, ведомость замечаний claude, действия (ответить за клиента, повторить, отменить), заметки.
- `/admin/clients`, `/admin/workers`, `/admin/metrics`.

- Сборка фронтов в образ Caddy, кабинет на `/`, пульт на `/admin`.
- E2E браузерные тесты (Playwright) на фейковых агентах: тестовый клиент проходит весь цикл с доработкой, админ видит и разбирает заказ.

**Готово, когда:** весь цикл проходит в браузере, включая доработку, а админ разбирает тот же заказ в пульте.

## Риски

- **Поведение CLI меняется между версиями** (флаги, формат JSONL) → фиксируем проверенные версии в конфиге воркера, парсеры терпимы к неизвестным событиям, сырые логи хранятся целиком.
- **КОМПАС и Office зависают или оставляют окна** → таймауты этапов, Job Objects, принудительное закрытие после этапа.
- **Агент не кладёт PDF в `preview/`** → воркер сам конвертирует docx/xlsx в PDF (Word/Excel через COM или LibreOffice), если PDF нет.
- **Долгие работы** → lease продлевается heartbeat'ом, таймаут этапа настраивается.
